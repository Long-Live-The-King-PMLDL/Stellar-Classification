# Раздел 2. Baselines — воспроизведение публичных решений

## 2.1. Задача этапа

Согласно ТЗ (требование 1), проект должен тестировать несколько существующих
решений и рассчитывать для них метрики. В качестве «существующих решений»
использованы публичные ноутбуки сообщества Kaggle, опубликованные для данного
датасета (Stellar Classification Dataset — SDSS17) и его синтетической версии
(Playground S6E6).

Задачи этапа:
1. Отобрать публичные решения, репрезентативные по разнообразию подходов
   (бустинг / классические модели / нейросеть).
2. Воспроизвести каждое решение на едином протоколе проекта (единый сплит,
   единая функция метрик, однократное использование test set).
3. Зафиксировать и устранить методологические проблемы оригиналов (утечки).
4. Получить честные метрики для сравнения с предлагаемой моделью.

## 2.2. Единая функция метрик

Первым артефактом роли стала общая для всего проекта функция `evaluate()`
(`src/evaluation/metrics.py`), используемая всеми моделями проекта, включая
предлагаемую MLP:

- вход: `y_true (n,)`, `y_proba (n, 3)`; предсказание = `argmax` по вероятностям;
- метрики: **macro-F1 (основная)**, accuracy, precision/recall по каждому классу,
  ROC-AUC (OvR, macro);
- порядок классов зафиксирован владельцем данных: GALAXY=0, QSO=1, STAR=2;
- функция покрыта тестами: идеальный классификатор (все метрики = 1.0),
  контрольный пример с вычисленными вручную значениями, случай отсутствия
  класса в выборке (ROC-AUC → NaN без падения).

Единая функция исключает расхождения из-за разных реализаций метрик и является
предпосылкой корректного сравнения всех моделей в разделе 5.

## 2.3. Отбор публичных решений

Критерии отбора:
- публичная доступность и воспроизводимость (видимые выходы ячеек);
- разнообразие подходов для содержательного сравнения;
- обучение на признаках датасета (не ансамблирование чужих предсказаний);
- читаемый код и доступные гиперпараметры.

Рассмотрены и отклонены:
- стек-ансамбль @cdeotte (S6E6): мета-логистическая регрессия поверх ~19
  файлов OOF-предсказаний чужих моделей — файлы недоступны, датасет
  синтетический, воспроизведение невозможно в принципе. Рецепт обучения LR
  внутри стека зафиксирован, но заменён самостоятельным NN-решением (S3).

Итоговый портфель — три источника, четыре модели:

| Решение | Метод | Источник |
|---|---|---|
| S1 | XGBoost + астрономический feature engineering | @emanuellcs, S6E6 |
| S2a | SVM (RBF, C=1) | @beyzanks, SDSS17 |
| S2b | Random Forest (default) | тот же ноутбук |
| S3 | Keras feed-forward NN (256/128/64) | @prtkpiyush, S6E6 |

## 2.4. Протокол воспроизведения

Каждое решение переносилось в код проекта с обязательным набором замен
(единых для всех бейзлайнов):

1. Данные — наши `train/val/test` из `data/processed/` (стратифицированный
   сплит 80/10/10, seed=42), собственные сплиты авторов удалялись;
2. Кодирование классов — предзаданная метка `label` (у всех авторов порядок
   совпал с нашим, у S2b неалфавитная кодировка GALAXY=0/STAR=1/QSO=2
   зафиксирована как отклонение, на функцию решения не влияет);
3. Метрики — только через `evaluate()`; заявленные метрики авторов
   цитируются отдельно и не сравниваются напрямую (другие сплиты и метрики);
4. seed=42; test использован один раз на решение;
5. атрибуция — ссылка на источник в шапке каждого файла решения.

## 2.5. Solution 1 — XGBoost с feature engineering

**Оригинал:** решение для S6E6: XGBoost (6000 деревьев, lr=0.015, depth=8,
subsample=0.75, colsample 0.7/0.8 и др.), sample_weight='balanced', multi-seed
(3) × 5-fold CV, OOF-смешивание и калибровка весов классов методом
дифференциальной эволюции; SDSS17 использовался как lookup-таблица для target
encoding. Feature engineering: 10 цветовых индексов, статистики магнитуд,
конверсия в потоки (10^(−0.4m), clip [0, 40]) и их статистики, sin/cos
координат, взаимодействия с redshift, категориальные астрономические бины
(spectral_type, galaxy_population, combo).

**Адаптации:** target encoding удалён (lookup из того же датасета = утечка;
компетишн-данных у нас нет; бины сохранены как категориальные фичи); multi-seed
CV → одно обучение с early stopping на val; balanced accuracy → macro-F1;
калибровка весов удалена (оптимизировала метрику автора, не macro-F1).

**Утечки в оригинале:** явных нет (CV по train, скейлера нет).

**Результат:** early stopping остановил обучение на итерации 1379 из 6000
(val) / 1509 (test-прогон).

## 2.6. Solution 2 — SVM (RBF) и Random Forest

**Оригинал:** ноутбук по SDSS17 с последовательностью: LocalOutlierFactor →
корреляции → feature selection (дроп alpha, delta, всех ID-колонок и cam_col,
остаток: u, g, r, i, z, redshift) → SMOTE → StandardScaler → holdout 33% →
SVC(rbf, C=1) и RandomForest(default) с визуализацией (confusion matrix, ROC,
class prediction error).

**Обнаруженные утечки (все применены ДО сплита):**
1. LOF-фильтрация выбросов на всём датасете;
2. SMOTE на всём датасете (синтетические строки содержат информацию о test);
3. StandardScaler.fit на всём датасете;
4. `spec_obj_ID` оставлен как фича — жёсткая утечка: по документации датасета
   одинаковый ID означает одинаковый класс; вероятный главный источник
   завышенных метрик автора.

**Адаптации:** все четыре утечки устранены — LOF исключён (артефакты −9999 уже
удалены на этапе подготовки данных), SMOTE заменён на `class_weight='balanced'`,
скейлер фитится только на train, ID-фича невоспроизводима (ID-колонки
отсутствуют в наших данных). SVM обучен на стратифицированной подвыборке
20 000 строк (сложность RBF SVC ~O(n²)) с `probability=True` (внутренняя
5-fold Platt-калибровка) для работы `evaluate()`. Гиперпараметры обеих моделей
и выбор фичей автора сохранены.

## 2.7. Solution 3 — Keras нейросеть

**Оригинал:** S6E6, обучение на объединении компетишн-данных и SDSS17
(флаг is_orig), 5-fold CV, balanced accuracy. Архитектура: Dense(256)-BN-
Dropout(0.3) → Dense(128)-BN-Dropout(0.3) → Dense(64)-Dropout(0.2) → softmax(3);
Adam(1e-3), sparse categorical CE, batch 2048, до 200 эпох, EarlyStopping
(patience=15, restore_best_weights), ReduceLROnPlateau (factor 0.5, patience 6).
Feature engineering: цветовые индексы, статистики магнитуд, log1p по потокам,
спектральный наклон и кривизны, взаимодействия с redshift, циклические
координаты, ординальные спектральные бины.

**Адаптации:** обучение на нашем train (без объединения); CV → одно обучение с
ES на val; метрика → macro-F1. Исправлена особенность оригинала: спектральные
бины вычислялись только для внешнего фрейма, поэтому `spectral_ord` был
константой −1 для обучающих строк, а категориальные признаки фактически не
использовались — в нашей версии бины считаются для всех строк.

**Утечки в оригинале:** не обнаружено (скейлер фитился внутри фолда — корректно).

## 2.8. Результаты

Таблица 1. Метрики воспроизведённых решений (единый протокол; macro-F1 —
основная метрика).

| Решение | val macro-F1 | test macro-F1 | test accuracy | test ROC-AUC | Время обучения |
|---|---|---|---|---|---|
| S1 XGBoost + FE | 0.97647 | 0.97467 | 0.97780 | 0.99675 | 50.7 c |
| S2a SVM (RBF) | 0.96074 | 0.95650 | 0.96130 | 0.99040 | 18.5 c (20k сабсэмпл) |

## 2.9. Анализ

1. **Насыщение задачи.** Все четыре решения укладываются в диапазон ~2 п.п.
   (0.956–0.976 по test macro-F1): признак redshift почти идеально разделяет
   классы, поэтому сложность решения не даёт преимущества.
2. **Default RF ≥ тюнингованный XGBoost** (0.97569 vs 0.97467): дефолтный лес
   на шести отобранных автором признаках сопоставим с бустингом на
   расширенном наборе из ~40 инженерных признаков — дополнительное
   свидетельство насыщения.
3. **Нейросеть (0.96988) уступает деревьям**, но заметно выше SVM — ожидаемый
   результат для табличных данных малой размерности.
4. **Устойчивость протокола.** Все отклонения val→test ≤ 0.005
   (XGBoost −0.0018; SVM −0.0042; RF +0.0008; NN +0.0018) — переобучения нет;
   положительные дельты RF и NN лежат в пределах шума выборки.
5. **Утечки — типичная проблема публичных решений:** в 2 из 3 источников
   препроцессинг выполнялся до сплита (SMOTE, скейлер, LOF), в одном
   использовалась ID-фича, почти детерминирующая класс. Наши цифры честные
   и в ряде случаев ниже заявленных авторами — это ожидаемое следствие
   корректного протокола.

## 2.10. Вклад в инфраструктуру проекта

Помимо бейзлайнов, роль внесла общие компоненты, используемые всеми моделями
проекта:
- `src/evaluation/metrics.py` — единая функция метрик с тестами;
- `src/utils/paths.py` — централизованные пути (работа из любой директории);
- `src/data/loading.py` — общий загрузчик с контрактом фичей и таргета;
- шаблон решения `solution_*.py` (единая структура: атрибуция → FE → модель →
  прогон → npz), воспринятый остальными ролями для предлагаемой модели;
- формат предсказаний `reports/preds/<model>_test.npz` (y_true + y_proba) для
  анализа ошибок и confusion matrix в разделе 5.

## 2.11. Ограничения

- SVM обучен на подвыборке 20 000 из ~80 000 (сложность RBF SVC) — его метрики
  консервативны, полное обучение могло бы дать ~+0.005.
- Два источника — решения для синтетической версии датасета (S6E6); перенос на
  SDSS17 выполнен с сохранением метода, но не полностью идентичен оригиналу.
- `redshift` сохранён в признаках (как у всех авторов): это даёт сравнимые с
  сообществом цифры, но делает задачу близкой к тривиальной — обсуждение в
  Limitations (раздел 7).
